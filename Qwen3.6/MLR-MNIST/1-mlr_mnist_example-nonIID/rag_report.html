File descriptions

Python Files (.py)

File: client_app.py
This Python file defines a Flower ClientApp for federated learning using PyTorch, specifically tailored for an MNIST classification task. It implements two core methods: train and evaluate, which handle the local training and evaluation of a neural network model on partitioned data. The client loads model weights from the global server, performs local training or evaluation using its assigned data partition, and returns updated model parameters and performance metrics. The implementation supports model persistence across rounds via the client's state management, allowing for optional local weight storage. The file integrates with Flower's distributed computing framework to enable federated learning workflows where multiple clients collaboratively train a shared model while keeping their data localized.

File: server_app.py
This Python file defines the main server application for a federated learning system using the Flower framework. It sets up and runs a federated training process where a global model is trained across multiple clients over several rounds. The server loads a global model, initializes a custom federated learning strategy (CustomStrategy), and manages the training loop by coordinating client interactions through a Grid. During each round, it evaluates the global model on local test data from the server's test directory, aggregates updates from clients, and saves the final trained model to disk after completing the specified number of rounds. The evaluation function dynamically loads and combines test data from multiple .npz files to compute accuracy and loss metrics for the global model at each round.

File: strategy.py
This file defines a custom federated learning strategy named CustomStrategy that extends the standard FedAvg algorithm from Flower. Its primary purpose is to enhance the basic FedAvg functionality by adding features such as saving model checkpoints when improved performance is achieved, persisting training and evaluation metrics to JSON files, and logging these results to Weights & Biases (W&B) for experiment tracking. The strategy manages the complete federated learning loop including training rounds, client-side aggregation, server-side evaluation, and maintains a record of the best-performing global model based on accuracy. It also implements a simple learning rate scheduling mechanism that reduces the learning rate at a specified round. The class integrates with Flower's server application framework to coordinate communication between clients and manage the federated training process while providing enhanced monitoring and artifact storage capabilities.

File: task.py
This Python file defines the core components of a federated learning application using the Flower framework with PyTorch. It implements a simple neural network classifier for MNIST-like image data, along with training and evaluation functions that operate on partitioned datasets. The Net class defines a basic feedforward neural network with a single linear layer for classification. The train function performs local training on a given dataset using stochastic gradient descent, while the test function evaluates model performance. The NPZDataset class handles loading data from .npz files, which contain preprocessed MNIST-style data partitions. The load_data function manages data loading for specific client partitions, enabling federated training across multiple data sources. Additionally, the create_run_dir utility creates timestamped directories for saving experiment results and configuration files. This setup allows for distributed training where each client trains on its local data partition and communicates updates to a central server through the Flower framework.

Since the network is not expensive nor intermittent, it is acceptable to perform frequent local updates without significant penalty on communication costs. However, given the strict latency requirement, any optimization must prioritize fast convergence and low computational load per node. Reducing model size and complexity through pruning or quantization techniques ensures efficient execution while maintaining acceptable performance.

Given that the nodes operate under an IID data distribution and do not support segment sharing, federated averaging should remain the primary aggregation method. Since partial offloading is not allowed, each node must independently execute full inference tasks locally, which increases thermal load. To mitigate thermal stress, dynamic voltage and frequency scaling (DVFS) should be applied to limit peak CPU usage when temperature exceeds 70°C but remains below critical thresholds.

For thermal management, since no active cooling is specified and temperatures above 70°C may trigger throttling, scheduling inference tasks during periods of lower ambient heat or reducing task frequency can help maintain stable operating conditions. When telemetry indicates a node reaches 63.4°C, adjusting model execution frequency or deferring non-critical computations can prevent overheating and preserve system stability.

Because the task involves time-series sensor data for bearing failure prediction, model compression techniques such as knowledge distillation or lightweight neural architecture search should be employed. These methods reduce computational requirements and thus lower energy consumption and heat generation. Since latency constraints are strict, models must be designed to meet real-time response demands without sacrificing too much accuracy.

The absence of segment sharing limits collaborative optimization across nodes. Therefore, local model adaptation strategies, such as personalized federated learning, should be avoided unless explicitly enabled. Instead, focus on optimizing global model updates to ensure convergence within the required timeframe and energy budget. Given the lack of intermittent connectivity, continuous training cycles are feasible, but must be balanced against thermal and power constraints.

To summarize, recommendations include deploying lightweight models, applying DVFS for thermal regulation, minimizing communication overhead, and ensuring that inference tasks align with the strict latency deadline.
