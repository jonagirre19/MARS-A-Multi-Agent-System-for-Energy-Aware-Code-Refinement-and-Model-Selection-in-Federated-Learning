File Descriptions

client_app.py

This file defines the client-side logic for a Federated Learning system using the Flower ClientApp abstraction and PyTorch. Its primary purpose is to encapsulate the local training and evaluation workflows that will be executed on distributed nodes.

The script implements two main entry points: 1. The train function: Decorated with @app.train(), this handles the local training cycle. It receives the global model weights from the server via a Message, loads them into a local Net instance, and fetches a specific data partition based on the node's configuration (partition-id). It executes the training process using a helper function train_fn, persists the resulting model state locally using context.state for potential future use, and returns the updated model weights and training metrics (loss and sample count) back to the server.

2. The evaluate function: Decorated with @app.evaluate(), this handles the local validation cycle. It initializes the model with the current global weights, loads the corresponding validation data partition, and uses the test_fn helper to calculate the evaluation loss and accuracy. These metrics are then packaged into a MetricRecord and sent back to the server.

Additionally, the file includes utility functions (save_model_to_state and load_model_from_state) to manage the persistence of model weights within the Flower context, enabling the client to maintain state across different training rounds.

server_app.py

This file defines the ServerApp, the central orchestration component of a Flower Federated Learning system. Its primary purpose is to manage the lifecycle of the federated learning process, specifically coordinating the training of a PyTorch neural network across multiple clients.

The script performs several key functions: 1. Configuration Management: It extracts hyperparameters and environment settings (such as the number of rounds, client sampling fractions, and hardware device) from the Context object provided by the Flower framework. 2. Model Initialization: It initializes the global PyTorch model (Net) and converts its state dictionary into an ArrayRecord, which is the standard format used by Flower to transmit weights between the server and clients. 3. Strategy Execution: It instantiates a CustomStrategy (a specialized version of FedAvg) and triggers the federated training loop via strategy.start(). This process manages the distribution of the global model, the collection of client updates, and the aggregation of weights over a specified number of communication rounds. 4. Centralized Evaluation: It implements a custom global evaluation function (get_global_evaluate_fn). This function monitors the global model's performance at the end of each round by loading test data from local .npz files, aggregating them into a PyTorch DataLoader, and calculating the loss and accuracy. 5. Persistence: After the training rounds are completed, it extracts the final aggregated weights from the result and saves the model to disk as final_model.pt.

strategy.py

This file defines a CustomStrategy class that extends the FedAvg strategy within a Flower Federated Learning environment. Its primary purpose is to augment the standard Federated Averaging process with advanced lifecycle management, experiment tracking, and model persistence.

Key functionalities implemented in this file include:

  • Enhanced Training Orchestration: It overrides the start method to manage the full federated learning loop, including the distribution of configurations, collection of client updates via a Grid, and the aggregation of both training and evaluation metrics.
  • Dynamic Hyperparameter Scheduling: It overrides configure_train to implement a basic learning rate decay schedule (specifically reducing the learning rate by half at round 5), allowing the server to adjust training parameters dynamically across rounds.
  • Model Checkpointing: It includes a mechanism (_update_best_acc) to monitor global model performance on the server side. When a new best accuracy is achieved, the current global model weights are converted to a PyTorch state dictionary and saved as a .pth file to the local filesystem.
  • Experiment Tracking and Logging:
    • Weights & Biases (W&B): It integrates wandb to log aggregated training and evaluation metrics in real-time for each round.
    • JSON Persistence: It implements save_metrics_as_json to maintain a persistent history of training and evaluation metrics (from both client-side and server-side evaluations) in a JSON file.
  • Dual Evaluation Support: The strategy is designed to handle both decentralized evaluation (where clients report metrics) and centralized evaluation (where the server evaluates the global model using a provided evaluate_fn).

task.py

This file, task.py, serves as the core machine learning definition layer for a Flower Federated Learning project. It decouples the model architecture, training logic, and data handling from the federated communication logic, providing a set of reusable utilities that the Flower Client will invoke during the training process.

The file's primary responsibilities include:

  • Model Architecture: It defines a simple PyTorch neural network (Net), which is a linear classifier (single-layer perceptron) designed for image-like data (e.g., MNIST) by flattening inputs and applying a log-softmax activation.
  • Training and Evaluation Logic: It implements the train and test functions. These are agnostic helper functions that handle the standard PyTorch training loop (SGD optimizer, CrossEntropyLoss) and validation logic, returning metrics like average loss and accuracy.
  • Custom Data Loading: It implements a custom NPZDataset class that inherits from torch.utils.data.Dataset. This allows the system to load partitioned data stored in .npz (NumPy) files, which is a common way to simulate Non-IID (Non-Independent and Identically Distributed) data across different federated clients.
  • Federated Partitioning Support: The load_data function enables the system to load specific data shards based on a partition_id. This ensures that each client in the federated network accesses only its designated local slice of the dataset.
  • Experiment Tracking: The create_run_dir utility manages the filesystem by creating timestamped directories to store run configurations and results, ensuring that different federated learning experiments are logged separately.

Recommendations from the RAG System

Since the nodes are battery-powered and do not rely on renewable energy excess, energy efficiency must be optimized through local computation and communication strategies that minimize power consumption. Given that the network is not expensive or intermittent, it is possible to implement periodic synchronization with reduced frequency to lower energy usage without compromising convergence.

Since latency has a strict deadline, model updates must be batched efficiently to meet timing constraints while avoiding excessive computation per node. This requires optimizing the local training loop to balance accuracy and speed, particularly considering that the nodes have identical class distributions and no partial offloading is allowed.

Given that the telemetry does not indicate high CPU usage or temperature, no immediate thermal mitigation is required. However, to prevent potential overheating under sustained load, dynamic voltage and frequency scaling (DVFS) should be applied when CPU usage exceeds moderate levels. This will help maintain performance within safe thermal limits.

Since the system does not support segment sharing or partial offloading, model compression techniques such as quantization or pruning must be applied locally before transmission to reduce bandwidth requirements and associated energy costs.

Because the task involves time-series sensor data for bearing fault prediction, local models should be kept lightweight and updated infrequently to align with the strict latency requirements. Training iterations should be minimized per node to avoid unnecessary energy expenditure, especially since there is no allowance for flexible scheduling or adaptive sampling rates.

The absence of renewable energy access negates the possibility of leveraging green computing strategies. Therefore, optimization must focus on minimizing computational overhead and ensuring efficient local processing to sustain long-term operation under fixed power budgets.

For any node operating above 70°C, throttling should be enforced to protect hardware integrity. Since no thermal mitigation is recommended below this threshold, proactive monitoring and control of compute intensity remain critical to maintaining stable operation.
