File descriptions

client_app.py

This file defines the ClientApp for a Flower Federated Learning system, acting as the entry point for the client-side logic using the Flower Next (Flower 1.x+) architectural pattern. Its primary purpose is to abstract the local training and evaluation processes, allowing them to be executed on distributed nodes.

The script implements two main decorated functions:

  • @app.train(): This function handles the local training cycle. It initializes the neural network (Net), synchronizes it with the global model weights received from the server via a Message, and loads a specific data partition based on the node's configuration (partition-id). It then invokes a training utility (train_fn) using hyperparameters provided by the server (like learning rate) and local configurations (like epochs). Finally, it returns the updated model weights and training metrics (loss and sample count) wrapped in a Message and RecordDict.
  • @app.evaluate(): This function handles local model validation. It loads the global model weights, accesses the local validation dataset, and computes performance metrics (loss and accuracy) using the test_fn utility. These metrics are then sent back to the server to monitor the global model's convergence.

Additionally, the file includes helper functions (save_model_to_state and load_model_from_state) that utilize the context.state object. This mechanism allows the client to persist model states between training rounds, providing a foundation for implementing personalized federated learning or continuing training from a local checkpoint.

server_app.py

This file defines the ServerApp, which acts as the central orchestration hub for a Federated Learning system using the Flower framework. Its primary purpose is to manage the global model lifecycle, coordinate the training process across clients, and evaluate the aggregated model's performance on a centralized test set.

Key responsibilities include:

  • Configuration Management: It extracts hyperparameters from the run_config (such as the number of rounds, client fractions, and target device) to initialize the training environment.
  • Strategy Orchestration: It instantiates a CustomStrategy (likely an extension of FedAvg) and triggers the federated learning process using strategy.start(), passing the initial model weights (as ArrayRecord) and client configurations.
  • Centralized Evaluation: It implements get_global_evaluate_fn, a custom evaluation loop that runs at the end of each server round. This function dynamically loads partitioned test data from .npz files located in a specific directory, aggregates them into a PyTorch DataLoader, and uses the current global model to calculate accuracy and loss.
  • Model Persistence: It handles the initialization of the global neural network (Net) and ensures that the final trained model weights are saved to disk as final_model.pt after all rounds are completed.
  • Environment Setup: It utilizes a helper function create_run_dir to organize logs and results based on the current run configuration.

strategy.py

The strategy.py file defines a CustomStrategy class that extends the FedAvg (Federated Averaging) strategy within the Flower framework. Its primary purpose is to manage the federated learning lifecycle—including training coordination, model aggregation, and evaluation—while adding advanced production-level monitoring and persistence features.

Key functionalities implemented in this file include:

  • Lifecycle Management: It overrides the start method to orchestrate the communication loop between the server and clients via a Grid. It manages the sequential execution of training and evaluation phases across multiple rounds.
  • Hyperparameter Scheduling: It overrides configure_train to implement a basic learning rate decay schedule (e.g., halving the learning rate at round 5), allowing the server to dynamically adjust client training configurations.
  • Model Checkpointing: The _update_best_acc method monitors the global model's accuracy. When a new "best" accuracy is achieved during server-side evaluation, the current global model state is serialized and saved to the filesystem as a .pth file.
  • Experiment Tracking: It integrates with Weights & Biases (W&B) to log training and evaluation metrics in real-time, providing visual tracking of the federated learning progress.
  • Results Persistence: The save_metrics_as_json method ensures that metrics from the client-side training, client-side evaluation, and server-side evaluation are appended to a local results.json file after every round, preventing data loss.
  • Evaluation Orchestration: It handles both decentralized evaluation (where clients evaluate the global model) and centralized evaluation (where the server evaluates the global model using a provided evaluate_fn).

task.py

The task.py file serves as the core machine learning module of the Federated Learning system, decoupling the model architecture, data handling, and training/evaluation logic from the Flower networking communication. Its primary purpose is to define the "task" that each client will perform during a federated round.

Key components include:

  • Model Definition: It defines a simple PyTorch neural network (Net) consisting of a linear layer and a log-softmax activation, designed for classification tasks (specifically tailored for MNIST-like data).
  • Training and Evaluation Logic: It implements agnostic train and test functions. The train function handles the SGD optimization loop and loss calculation, while the test function computes accuracy and loss on a validation set. These functions are called by the Flower Client during the fit and evaluate steps of the FL process.
  • Custom Data Pipeline: It implements an NPZDataset class to load partitioned data from .npz files, allowing the system to handle pre-split datasets locally on each client. The load_data function manages the mapping between a client's partition_id and its corresponding local data files.
  • Experiment Management: The create_run_dir utility ensures that each federated learning execution is logged in a timestamped directory, saving the UserConfig for reproducibility.

In summary, this file acts as the PyTorch backend that provides the necessary tools for the Flower client to load local data, train the global model locally, and report performance metrics back to the server.

Recommendations from the RAG system

Since the project involves real-time sensor data prediction for bearing fault detection, and latency has a strict deadline, optimization must prioritize minimizing computational overhead while maintaining model convergence under resource constraints. Given that nodes are not battery-powered, renewable energy is not applicable, and network limitations do not apply, the focus should be on reducing thermal stress and improving energy efficiency through computation-level optimizations.

Since the nodes operate in an IID environment where all clients have the same class distribution, federated averaging can proceed without complications from heterogeneous data skew. This allows for consistent model updates and reduces the need for complex reweighting strategies that could introduce additional latency or energy consumption.

Given that partial offloading is not allowed, local computation must be optimized entirely within node capabilities. Since network costs are not a concern, communication frequency may be adjusted to balance between convergence speed and power usage. However, since network intermittency is also not an issue, there's no requirement to implement robustness mechanisms against disconnections.

Since the system does not maximize precision, accuracy can be traded for energy efficiency, allowing for more aggressive pruning or quantization techniques during local training phases. This aligns with approaches seen in edge computing scenarios where performance is balanced against energy consumption.

For thermal management, given that current temperatures are below 70°C, no immediate action is required. However, if telemetry shows a temperature approaching 70°C, dynamic voltage and frequency scaling (DVFS) should be applied to reduce CPU load. This method is effective in managing heat generation when sustained high loads occur, such as during intensive training cycles.

If a node reports a temperature near or exceeding 70°C, throttling should be employed to prevent overheating. Since the system operates with fixed hardware resources and does not support renewable energy usage, thermal mitigation must rely on software-based adjustments rather than environmental interventions.

To ensure convergence despite limited communication and strict deadlines, local epochs should be tuned to optimize the trade-off between model staleness and training time. With no allowance for partial offloading, the entire training process must complete locally before any synchronization occurs, necessitating efficient local optimization strategies.

In the absence of segment sharing, each node must independently manage its own model updates. Therefore, compression techniques like quantization or sparsification should be used to reduce both computational load and memory footprint during local training sessions. These methods help maintain performance while reducing the likelihood of exceeding thermal thresholds due to prolonged computation.

Energy efficiency can be improved by applying early stopping criteria based on loss improvement trends observed in local training. This prevents unnecessary computation once model performance plateaus, thus conserving energy and reducing heat generation.

Finally, since the task involves temporal sensor data, models should be designed with low-latency inference in mind. Lightweight architectures such as mobile networks or compact CNN variants should be considered to minimize both training and inference times, ensuring compliance with the strict deadline requirements.
