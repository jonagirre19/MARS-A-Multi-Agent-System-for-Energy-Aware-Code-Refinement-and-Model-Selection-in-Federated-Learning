File descriptions

client_app.py

This file defines the client-side logic for a Federated Learning system using the Flower ClientApp abstraction. Its primary purpose is to encapsulate the local training and evaluation workflows that will be executed on distributed nodes.

The script performs the following key functions:

  • Client Lifecycle Management: It utilizes the @app.train() and @app.evaluate() decorators to define the specific behaviors the client should execute when triggered by the Flower server.
  • Model State Handling: It manages the synchronization of model weights. In the train function, it retrieves global model weights from the server's message and loads them into a PyTorch Net instance. It also includes helper functions (save_model_to_state and load_model_from_state) to handle local state persistence using RecordDict and ArrayRecord, allowing the client to maintain state across different federated rounds.
  • Data Partitioning: It dynamically loads a specific subset of the MNIST dataset based on the partition-id and num-partitions provided in the node_config, ensuring that each client trains on a unique shard of the data.
  • Local Training: The train function coordinates the local optimization process by invoking an external train_fn, passing configuration parameters (such as learning rate and local epochs) received from the server via run_config and msg.content.
  • Local Evaluation: The evaluate function implements the validation logic, loading the global model and calculating local performance metrics (loss and accuracy) using a local validation loader and an external test_fn.
  • Communication: It formats the results of local computation into Message objects containing RecordDict and MetricRecord, which are sent back to the server to be aggregated.

server_app.py

This file defines the ServerApp for a Flower-based Federated Learning system, serving as the central orchestrator for the training process. Its primary purpose is to manage the global model lifecycle, coordinate the aggregation strategy, and perform centralized evaluation.

Key responsibilities include:

  • Configuration Management: It extracts hyperparameters from the context.run_config, such as the number of server rounds, training/evaluation fractions, and the target hardware device.
  • Model Initialization: It initializes the global PyTorch model (Net) and wraps its state dictionary into a Flower ArrayRecord to be distributed to clients.
  • Strategy Execution: It instantiates a CustomStrategy and triggers the federated learning process via strategy.start(), passing the initial model arrays and a training configuration (learning rate).
  • Centralized Evaluation: It implements a get_global_evaluate_fn which performs server-side validation. This function dynamically loads testing data from .npz files in a specific directory, concatenates them into a PyTorch DataLoader, and uses a separate test utility to calculate the global loss and accuracy after each round.
  • Persistence: It handles the creation of run directories for logging and saves the final aggregated model state to a file named final_model.pt upon completion of all rounds.

strategy.py

This file defines CustomStrategy, a specialized federated learning strategy that extends the standard FedAvg (Federated Averaging) algorithm to provide advanced experiment management, monitoring, and model persistence. Its primary purpose is to orchestrate the training loop on the server side while adding production-grade tracking and scheduling capabilities.

Key functionalities implemented in this strategy include:

  • Experiment Tracking and Logging: It integrates with Weights & Biases (wandb) to log training and evaluation metrics in real-time for every round. It also implements a custom JSON logging mechanism (save_metrics_as_json) to persist performance history to the local filesystem.
  • Model Checkpointing: The strategy tracks the best global accuracy achieved across rounds. Through the _update_best_acc method, it automatically saves the global model's state dictionary as a .pth file whenever a new peak in accuracy is detected.
  • Dynamic Hyperparameter Scheduling: It overrides the configure_train method to implement a basic learning rate decay schedule, specifically reducing the learning rate by 50% at round 5 to refine convergence.
  • Orchestrated Execution Loop: The start method manages the entire federated lifecycle, coordinating the communication between the server and clients via a Grid. It handles:
    • Training Phase: Configuring rounds, sending global parameters to clients, and aggregating returned updates.
    • Distributed Evaluation: Managing evaluation tasks executed on the client side.
    • Centralized Evaluation: Executing a server-side evaluation function to validate the global model on a hold-out dataset.
  • State Management: It manages the transition of the global model parameters (ArrayRecord) and the accumulation of results into a Result object, which is returned after all specified rounds are completed.

task.py

This file, task.py, serves as the core machine learning definition module for a Flower Federated Learning project. Its primary purpose is to decouple the model architecture and the training/evaluation logic from the federated orchestration logic (client and server implementations).

The file performs the following specific functions:

  • Model Definition: It defines a simple neural network (Net) using PyTorch, consisting of a linear layer that flattens input data and applies a log-softmax activation, suitable for multi-class classification tasks (defaulting to MNIST-like dimensions).
  • Training and Evaluation Logic: It provides two agnostic functions, train() and test(). These handle the PyTorch-specific boilerplate: setting the model to the correct mode (train() vs eval()), managing device placement (CPU/GPU), calculating CrossEntropyLoss, and performing the optimization step via SGD.
  • Custom Data Handling: It implements a custom NPZDataset class inheriting from torch.utils.data.Dataset. This allows the system to load pre-processed NumPy arrays stored in .npz files, which is a common way to handle partitioned data in federated settings.
  • Data Partitioning Support: The load_data() function enables the loading of specific data shards based on a partition_id. This ensures that each Flower client loads only its assigned local subset of the training and testing data from the local filesystem.
  • Experiment Tracking: The create_run_dir() utility manages the creation of timestamped output directories to store run configurations and results, ensuring reproducibility and organized logging of the federated learning experiments.

Recommendations from the RAG system

Since the project involves real-time sensor data processing with strict latency deadlines and no allowance for partial offloading, optimization must focus on efficient local computation and minimal energy consumption without relying on cloud-based or shared resources. Given that nodes are not battery-powered and do not utilize renewable energy, direct energy-saving strategies through reduced activity or dynamic voltage scaling should be prioritized over green computing approaches.

Given that latency is strictly enforced and network conditions are stable (network is not expensive/limited or intermittent), model inference can be optimized for deterministic performance. Local model updates should be scheduled to minimize idle time while maintaining consistent response times. Since partial offloading is disallowed, each node must independently perform full inference tasks, making it critical to reduce computational overhead through model compression or quantization techniques that maintain accuracy within acceptable bounds.

Since the task involves temporal sensor data for bearing fault prediction, and given the IID nature of class distributions across nodes, federated averaging may converge effectively even with limited communication. Therefore, reducing frequency of global updates and increasing local epochs per round can lower communication overhead, which is beneficial under constrained network conditions, although network limitations are not indicated as a concern.

For thermal management, since temperature readings remain below 70°C, no immediate mitigation actions are required. However, monitoring CPU usage levels is crucial; when usage exceeds 75%, throttling may occur, leading to performance degradation. In such cases, limiting concurrent processes or reducing model complexity during high-load periods will prevent overheating and ensure sustained operation.

Since the system does not support segment sharing, models must be tailored per node's capabilities and constraints rather than adapting to shared architectures. This implies that edge devices must execute lightweight versions of the model that are compatible with their hardware specifications. Techniques like pruning or knowledge distillation can help reduce model size and power consumption while preserving predictive accuracy.

In summary, the most effective optimizations involve minimizing unnecessary computation, enforcing deterministic execution schedules, leveraging local model efficiency, and avoiding reliance on external factors like renewable energy or network flexibility due to project constraints. These measures collectively address energy efficiency, thermal stability, and convergence requirements within the defined operational parameters.
