File descriptions

client_app.py

This file defines the ClientApp for a Flower federated learning system, serving as the entry point for client-side logic in a PyTorch-based MNIST classification task. Its primary purpose is to encapsulate the local training and evaluation workflows that are triggered by the Flower server.

The script implements two main decorated functions:

  • @app.train(): This function handles the local training process. It initializes the neural network (Net), synchronizes it with the global model weights received from the server via a Message, and loads a specific data partition based on the node_config. It executes the training loop using a helper function (train_fn), persists the resulting model state locally within the context.state for potential future use, and returns the updated model weights and training metrics (loss and sample count) back to the server.
  • @app.evaluate(): This function handles the local validation process. It loads the global model weights and the corresponding validation data partition to compute evaluation metrics (loss and accuracy) using a helper function (test_fn). These metrics are then packaged into a MetricRecord and sent back to the server to monitor the global model's performance.

Additionally, the file includes utility functions (save_model_to_state and load_model_from_state) to manage model persistence using ArrayRecord and RecordDict, enabling the client to maintain state across different federated learning rounds.

server_app.py

This file defines the ServerApp, which serves as the central orchestration component of a Flower Federated Learning system. Its primary purpose is to manage the global model lifecycle, coordinate the federated training process, and perform centralized evaluation.

Key responsibilities include:

  • Initialization and Configuration: It extracts runtime hyperparameters (such as the number of rounds, client sampling fractions, and hardware device) from the Context object and initializes the global model architecture using the Net class.
  • Strategy Orchestration: It instantiates a CustomStrategy (based on FedAvg) and executes the training loop via strategy.start(). This process handles the distribution of the initial model weights to selected clients and the aggregation of updated weights over the specified number of rounds.
  • Global Evaluation: It implements a custom evaluation function (get_global_evaluate_fn) that allows the server to validate the global model's performance on a centralized test set. This function dynamically loads dataset shards stored as .npz files from a specific directory, aggregates them into a PyTorch DataLoader, and computes the loss and accuracy using a separate test utility.
  • Persistence: It manages the creation of run directories for logging and saves the final aggregated model state to a file (final_model.pt) once the federated training process is complete.

strategy.py

This file defines CustomStrategy, a specialized federated learning strategy that extends the FedAvg (Federated Averaging) algorithm within the Flower framework. Its primary purpose is to enhance the standard aggregation process with lifecycle management, experiment tracking, and model persistence.

Key functionalities include:

  • Enhanced Lifecycle Management: It overrides the start method to orchestrate the complete federated learning loop, managing the interaction between the server and the client grid across multiple rounds of training and evaluation.
  • Experiment Tracking: It integrates with Weights & Biases (wandb) to log training and evaluation metrics in real-time, allowing for remote monitoring of the global model's convergence.
  • Model Checkpointing: It implements a "best-model" saving mechanism via _update_best_acc. If the server-side evaluation shows a new peak in accuracy, the current global model state is serialized and saved as a .pth PyTorch file.
  • Dynamic Hyperparameter Scheduling: It overrides configure_train to implement a basic learning rate decay schedule (e.g., halving the learning rate at round 5), demonstrating how to dynamically update client configurations during the training process.
  • Result Persistence: It includes a utility method save_metrics_as_json that incrementally writes training and evaluation metrics (from both client-side and server-side evaluations) to a local JSON file for offline analysis.
  • Hybrid Evaluation: The strategy supports both distributed evaluation (aggregated from clients) and centralized evaluation (performed directly on the server using a provided evaluate_fn).

task.py

The task.py file serves as the core machine learning module that defines the model architecture, training logic, and data handling pipeline used by both the Flower server and clients. Its primary purpose is to decouple the PyTorch-specific implementation from the federated learning orchestration logic.

Key responsibilities of this file include:

  • Model Definition: It defines a simple fully connected neural network (Net) designed for classification tasks (defaulting to MNIST dimensions), providing the structural blueprint that will be synchronized across all participants in the federated network.
  • Training and Evaluation Logic: It implements the train and test functions, which encapsulate the standard PyTorch training loop (optimizer, loss function, and backpropagation) and evaluation metrics (accuracy and loss). These functions are intended to be called by the Flower Client during the fit and evaluate steps of the federated learning rounds.
  • Custom Data Loading: It implements a specialized NPZDataset class and a load_data utility to handle partitioned datasets stored in .npz format. This allows each client to load only its specific shard of the data based on a partition_id, which is fundamental for simulating non-IID (independent and identically distributed) data distributions in federated learning.
  • Experiment Management: The create_run_dir function provides a utility for organizing results by creating timestamped directories and saving the runtime configuration as a JSON file, ensuring reproducibility of the federated experiments.

However, since partial offloading is not allowed, the system must perform all computations locally, increasing the need for efficient local processing strategies such as model compression or pruning to reduce both energy usage and thermal generation.

For thermal management, given that temperature readings remain below 70°C, no active cooling or throttling measures are required. If telemetry indicates sustained high CPU usage above 75%, dynamic model adaptation or selective feature extraction could be employed to reduce compute load during peak periods, ensuring continued operation within thermal limits while meeting latency constraints.
