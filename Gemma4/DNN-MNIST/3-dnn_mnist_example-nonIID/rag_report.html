File descriptions

client_app.py

This file defines the client-side logic for a Federated Learning system using the Flower ClientApp abstraction, specifically designed for a PyTorch-based MNIST classification task. Its primary purpose is to encapsulate the local training and evaluation workflows that are executed on distributed nodes.

The script implements two main event handlers:

  • @app.train(): This function handles the local training process. It initializes the neural network (Net), synchronizes the model weights with the global parameters received from the server via msg.content, and loads a specific data partition based on the node's configuration (partition-id). It then executes the training loop using a helper function (train_fn), persists the resulting model state locally using save_model_to_state for potential future use or personalization, and returns the updated model weights and training metrics (loss and sample count) back to the server.
  • @app.evaluate(): This function manages the local validation process. It loads the global model weights, accesses the validation subset of the local data partition, and calculates performance metrics (evaluation loss and accuracy) using the test_fn helper. These metrics are then packaged into a MetricRecord and sent back to the server to monitor the global model's performance.

Additionally, the file includes utility functions (save_model_to_state and load_model_from_state) that utilize Flower's RecordDict and ArrayRecord to handle the serialization and persistence of PyTorch state dictionaries, enabling the client to maintain state across different training rounds.

server_app.py

This file defines the ServerApp for a Flower Federated Learning system, serving as the central orchestrator for the training process. Its primary purpose is to manage the global model's lifecycle, coordinate the federated learning rounds, and evaluate the model's performance on a centralized test set.

Key responsibilities include:

  • Orchestration: It uses the ServerApp and Grid abstractions to handle the communication and distribution of tasks across the federated network.
  • Configuration Management: It extracts hyperparameters (such as the number of rounds, training/evaluation fractions, and device settings) from the Context run configuration.
  • Strategy Implementation: It initializes a CustomStrategy (a subclass of a Flower strategy, likely implementing a variant of FedAvg) and configures it with specific directory paths for saving results.
  • Global Model Management: It initializes the global PyTorch model (Net), converts its state dictionary into an ArrayRecord for transmission to clients, and saves the final aggregated model to disk as final_model.pt after the training rounds are complete.
  • Centralized Evaluation: It implements a global evaluation function (get_global_evaluate_fn) that loads fragmented test data from .npz files in a specific directory, aggregates them into a PyTorch DataLoader, and computes the global loss and accuracy for the model at the end of each server round.

strategy.py

The strategy.py file defines a CustomStrategy class that extends the standard FedAvg (Federated Averaging) strategy within the Flower framework. Its primary purpose is to enhance the federated learning orchestration process by integrating experiment tracking, model persistence, and dynamic hyperparameters.

Key functionalities provided by this file include:

  • Experiment Tracking: It integrates with Weights & Biases (wandb) to log training and evaluation metrics (from both clients and the server) in real-time across federation rounds.
  • Model Checkpointing: It implements a "best model" saving mechanism via _update_best_acc. When the server-side evaluation reveals a new peak in accuracy, the global model's state dictionary is saved as a .pth file to the local filesystem.
  • Persistence of Metrics: It includes a utility to export round-by-round performance metrics (training and evaluation) into a results.json file for post-hoc analysis.
  • Dynamic Hyperparameter Scheduling: It overrides the configure_train method to implement a basic learning rate scheduler, specifically reducing the learning rate by half at the fifth round of training.
  • Execution Orchestration: The start method manages the full federated lifecycle: coordinating the distribution of global parameters to clients via the Grid, aggregating returned updates, performing centralized server-side evaluation, and updating the global model.

task.py

The task.py file serves as the core machine learning utility module for a Flower-based Federated Learning system. It abstracts the model architecture, training/evaluation logic, and data handling to ensure consistency across both the server and multiple clients.

Specifically, the file performs the following functions:

  • Model Definition: It defines a simple neural network (Net) consisting of two fully connected layers, designed for classification tasks (specifically tailored for flattened 28x28 images, such as MNIST).
  • Training and Evaluation Logic:
    • The train function implements a standard PyTorch training loop using Stochastic Gradient Descent (SGD) and Cross-Entropy Loss.
    • The test function evaluates the model's performance on a given dataset, returning the loss and accuracy. Both functions are designed to be device-agnostic (supporting CPU/GPU).
  • Data Management:
    • It implements a custom NPZDataset class that inherits from torch.utils.data.Dataset to load training and testing data from NumPy .npz files.
    • The load_data function handles the loading of specific data partitions based on a partition_id, which is critical for simulating non-IID (Independent and Identically Distributed) data across different federated clients.
  • Experiment Tracking: The create_run_dir function manages the organization of outputs by creating timestamped directories and saving the run configuration as a JSON file for reproducibility.

Recommendations from the RAG system

Since the nodes are battery-powered and do not have access to renewable energy excess, traditional approaches relying on green energy for training are not applicable. Energy efficiency must be achieved through local computation optimization rather than external power source utilization.

Given that latency has a strict deadline and partial offloading is not allowed, model inference and training must be performed entirely on-device. This necessitates optimizing model size and computational complexity to meet timing constraints while minimizing power consumption.

Since the network is not expensive or intermittent, communication overhead between nodes and the central server can be managed without strict bandwidth limitations. However, this does not eliminate the need for efficient data transmission strategies during aggregation phases.

The absence of segment sharing implies that each node must independently manage its own model updates and computations without leveraging shared segments from other nodes. Thus, individual node-level optimizations become critical for performance and energy efficiency.

For thermal management, since temperature readings are within normal bounds (< 70°C), no immediate action is required. However, monitoring CPU usage levels is essential; when usage exceeds moderate thresholds, adjustments should be made to prevent overheating or throttling.

To address energy efficiency, models should be compressed or quantized to reduce both memory footprint and compute requirements. Given the IID nature of data across nodes, federated averaging can proceed reliably with minimal risk of divergence due to non-iid conditions.

Given that precision is not maximized, techniques such as pruning or knowledge distillation may be employed to further reduce model size without significantly impacting accuracy. These methods align well with the requirement for low-latency execution and constrained device resources.

In cases where telemetry indicates increasing CPU usage approaching high levels (>75%), dynamic scaling of model complexity or reduced sampling frequency of sensor inputs could mitigate excessive energy consumption and potential thermal stress.

Model convergence remains feasible under current settings due to balanced data distribution and lack of significant network limitations. Nonetheless, periodic evaluation of convergence metrics is advised to detect any drift caused by environmental variability or hardware degradation over time.
